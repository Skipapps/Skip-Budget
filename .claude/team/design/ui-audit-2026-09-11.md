# UI audit — SkipBudget, branch `almost-done-all-pages`

Date: 2026-09-11 · Author: Priya (Product Design lead)
Scope: `src/theme`, `src/components`, all 54 screens under `src/app`.
Areas attributed: **Pia** — onboarding, auth, budgets, transactions, bills, subscriptions, splits, everyday screens. **Paulo** — loans, calculator, schedule, savings, insights, settings, appearance, notifications, Pro paywall.

No screen code was edited in this pass.

---

## Headline

The design system is in better shape than the screens that consume it. `src/theme/palette.ts`
is genuinely good work: one accent over one neutral ramp, a measured `onColor()` so foregrounds
are computed rather than guessed, and `readable()` so pale accents can still be type. Dynamic
type is capped almost everywhere, `Switch` is themed identically in all four places it appears,
and the list screens have a proper four-state pattern.

Almost every defect below is a **place that bypassed the system it already has**, not a missing
system. That makes them cheap to fix and safe to approve one at a time.

Two findings are not cosmetic and are flagged as blockers: the paywall ships debug output, and
`insights.tsx` renders money figures that are wrong when a fetch fails.

## 1. Controls draw white on the accent instead of `onControl` — S

Files: `src/components/navigation/skip-tab-bar.tsx:77`, `src/components/dashboard/add-button.tsx:24`,
`src/app/source/[id].tsx:111`, `src/components/ui/multi-choice-chips.tsx:46`

`buildTokens()` computes `onControl` precisely so a foreground on the accent is measured. Four
controls ignore it and hardcode white (or `colors.surface`). Three of them sit a few pixels from a
sibling that *does* use `text-on-control`, so the same pill renders a white icon beside near-black
type.

Focused tab icon, white on the accent fill:

| accent | white icon | label (`onControl`) |
|---|---|---|
| butter | 1.27:1 | near-black |
| honey | 1.58:1 | near-black |
| **apricot (default)** | **2.11:1** | near-black |
| blush | 1.51:1 | near-black |
| powder | 1.67:1 | near-black |
| sage | 1.86:1 | near-black |
| coral | 2.47:1 | near-black |
| lavender | 2.56:1 | near-black |
| rose | 2.72:1 | near-black |
| taupe | 3.30:1 | near-black |
| plum / slate | 8.38 / 8.59:1 | white — correct by luck |

The dashboard FAB is worse because it uses `colors.surface`, which breaks in *both* directions —
near-white on a pale accent in light mode, near-black on a dark accent in dark mode:

| accent | light | dark | with `onControl` |
|---|---|---|---|
| butter | 1.21 | 13.77 | 14.82 |
| apricot (default) | 2.01 | 8.33 | 8.96 |
| plum | 7.98 | **2.09** | 8.38 |
| slate | 8.18 | **2.04** | 8.59 |
| taupe | 3.14 | 5.32 | 5.73 |

11 of 12 accents fail in at least one mode. Taupe alone passes both.

**Change:** replace the hardcoded value with `colors.onControl` in all four. `src/app/appearance.tsx`
already does this correctly with `onColor(accent.value)` — copy that. One line each, no new tokens.

## 2. The Pro paywall renders debug output to users — S — Paulo — BLOCKER

File: `src/app/pro.tsx:195-199`, source `src/api/pro.ts:179-225`

When the store returns nothing the paywall prints:

    {prices.error
      ? `The store said: ${(prices.error as Error).message}`
      : 'The App Store returned no plans for this app yet. …'}
    {prices.data?.debug ? `\n\n[${prices.data.debug}]` : ''}

`debug` is built as `offerings=0 current=none pkgs=0 fetchErr=…`. The comment on `pro.ts:180` says
"shown while debugging billing". This is leftover scaffolding from commits 5343150 and 2409e0b and
it is on the revenue screen.

**Change:** delete the `debug` line from the render and keep `debug` behind `__DEV__` in `pro.ts`.
Replace the raw `error.message` with mapped copy — "We could not reach the App Store. Check your
connection and tap Check again." Keep the existing no-plans sentence, which is good.

## 3. `insights.tsx` handles no error state, and reports wrong money — M — Paulo — BLOCKER

File: `src/app/insights.tsx`

The screen runs eight queries (`useLedger`, `useCards`, `useSalarySources`, `useMonthlySavings`,
`useSubscriptions`, `useMyBalances`, `useSpendCategories`, `useSourceBalances`). It destructures
`isLoading` only. `isError` is never read, and every consumer falls back with `?? []` / `?? 0`.

A failed fetch therefore renders as a confident zero rather than as an error. The worst case is
line 96:

    const worth = savedTotal - owedOnCards + splitPosition;

If `useCards` fails, `owedOnCards` is `0` and **net worth is shown inflated by the user's entire
card debt**, with no indication anything failed. That breaches the team's money-accuracy rule —
a figure that does not match a statement is being presented as if it did.

`src/app/(tabs)/transactions.tsx` already has the right pattern: skeleton, error + retry, empty,
filtered-empty.

**Change:** aggregate the eight `isError` flags, and when any is set render `PageState` with
"We could not load your insights." / "Something went wrong fetching your figures. Nothing is lost."
and a "Try again" action wired to refetch. Never render a derived total from a failed query.

## 4. `useLedger` drops two of its five error flags — S — shared — BLOCKER

File: `src/api/queries.ts:169`

    isError: receipts.isError || subscriptions.isError || bills.isError,

`salary.isError` and `charges.isError` are missing, but both feed `entries`. So if the salary or
charges query fails, every ledger screen — including the ones that correctly handle `isError` —
renders a ledger with income or recorded charges silently absent and **no error shown at all**.
Balances are wrong and the UI claims they are right.

**Change:** add `|| salary.isError || charges.isError`. One line. This is a data-layer fix;
hand to Dmitri rather than to a designer.

## 5. `cards.tsx` shows a blank region when a load fails — S — Pia

File: `src/app/(tabs)/cards.tsx:155-158, 204-207`

    {cards.isPending ? <Skeleton … /> : null}
    {!cards.isPending && cards.data?.length === 0 ? <EmptyNote … /> : null}

On error `data` is `undefined`, so `undefined?.length === 0` is `false`. The skeleton has stopped,
the empty note does not show, and there is no error branch — the user gets an unexplained blank
area where their cards were, with no retry. Both the Cards and Bank accounts sections behave this way.

**Change:** add an error branch using `PageState` with a "Try again" action, matching `bills.tsx`.
Also retire the local `EmptyNote` (`cards.tsx:62`) in favour of `PageState` so the Cards tab's
empty state stops looking different from every other list in the app.

## 6. `ml-13` is not a Tailwind class — the row dividers do nothing — S — Pia

Files: `src/app/(tabs)/home.tsx:347`, `src/app/bills.tsx:139`, `src/app/subscriptions.tsx:141`,
`src/app/source/[id].tsx:221`

    <View className="ml-13 h-px bg-line/60" />

Tailwind's default spacing scale has no `13` (…12, 14…), and `tailwind.config.js` extends only
`fontFamily`, `colors` and `screens` — no `spacing`. The class resolves to nothing, so the divider
renders **full-bleed at 0pt inset** on four screens.

The intent was right: the row icon is `h-10 w-10` (40pt) plus `gap-3` (12pt), so text starts at
52pt, and `ml-13` = 13 × 4 = 52pt exactly. It just was not a real class.

**Change:** `ml-[52px]`, or add `spacing: { 13: '3.25rem' }` to the config. Note
`src/components/settings/settings-row.tsx:112` uses `ml-8`, which is valid and does render — so
today two list styles disagree visibly.

## 7. The dashboard's loading state is the bare word "Loading" — S/M — Pia

File: `src/app/(tabs)/home.tsx:333-338`

    {loading ? 'Loading' : empty}

Plain muted text, no ellipsis, no skeleton. Every other list in the app uses `SkeletonList`. This is
the first screen after login and it has the least finished loading treatment; the word without
punctuation reads as placeholder copy.

**Change:** use `<SkeletonList rows={3} />` in both `Section` blocks, matching `transactions.tsx`.
Also add an error branch — `home.tsx` currently reads no `isError` anywhere.

## 8. The destructive red is not a token and fails AA in dark mode — S — shared

Files: `src/components/settings/settings-row.tsx:44,55`, plus `add-bill.tsx:470`,
`add-account.tsx:368`, `add-expense.tsx:352`, `add-receipt.tsx:570`, `add-card.tsx:304`,
`add-subscription.tsx:300`

`#DC2626` is hardcoded in seven files. It is not in `Tokens`, so it does not follow the mode:

| surface | ratio | AA 4.5 |
|---|---|---|
| light card `#FFFFFF` | 4.83 | pass |
| light surface `#FBF9F7` | 4.60 | pass |
| **dark card `#2A2634`** | **3.05** | **fail** |
| **dark surface `#1B181F`** | **3.63** | **fail** |

For comparison the theme's own dark `moneyOut` (`#ED7A7A`) scores 5.38 on the dark card — the ramp
already knows how to do this.

**Change:** add `danger` to `RAMPS` (light `#B85040`-family, dark `#ED7A7A`-family), expose it as a
`danger` token and a `text-danger` class, and replace all seven literals. This is the only genuine
dark-mode contrast failure found.

## 9. There is no shared section heading, so the three tabs disagree — M — shared

`src/components/ui/typography.tsx` exports `Title`, `Subtitle`, `Body`, `Quote`, `FieldLabel`,
`Strong` — but nothing for a section heading, which is the most common element after body copy.
Every screen invented one:

- **15px** semibold — splits, receipts, pro, bill-plans, subscription-plans, pro-feature, reminders, split-group, notifications, insights (rows)
- **16px** — appearance, savings, save-loan, source/[id]
- **17px** — home ×2, splits, loan-schedule, source/[id]
- **19px** — insights `Heading`
- **20px** — cards ×2, savings-month
- **21px bold** — splits · **18px bold** — reminders · **24px bold** — salary

Home says 17px, Cards says 20px, Insights says 19px. Three tabs, three sizes for the same thing,
visible by swiping.

Page titles drift the same way: `<Title>` carries `mt-1` (10×), `mt-2` (31×), `mt-3` (15×), `mt-4`,
`mt-5`, `mt-6`, `mt-10`, `mt-16`. Settings → Appearance shifts the title by 4pt for no reason.

**Change:** add `SectionHeading` to `typography.tsx` at **17px semibold** (the median, and what the
home tab already uses), migrate screens to it, and let `Screen` own the title offset so `mt-2`
becomes the default rather than a per-screen guess. Local `Heading` / `SectionHeader` helpers in
`insights.tsx` and `cards.tsx` fold into it.

## 10. `hello.tsx` navigates during render, with no loading guard — S — Pia

File: `src/app/hello.tsx:34`

    if (profile.data && (profile.data.display_name ?? '').trim()) {
      router.replace('/home');
      return null;
    }

Two problems. `profile.isLoading` is never checked, so while the profile loads `profile.data` is
undefined and the screen renders the full "What should friends call you?" form — a returning
Apple/Google user sees a flash of a name prompt before being bounced to Home. And `router.replace()`
is called in the component body during render, which React will warn about.

The comment says "waiting for the row costs one spinner frame", but no spinner exists.

**Change:** return a skeleton or null while `profile.isLoading`, and move the redirect into an
effect (or use `<Redirect href="/home" />`, which is the expo-router-sanctioned way to do this
declaratively).

## Open questions for the Founder

1. **Currency.** `formatCurrency` hardcodes `$`, and `mutations.ts:116` says "currency is fixed to
   USD" — but `profiles.currency` and `groups.currency` columns exist and are never read, and
   `expo-localization` is installed and used only for push. A non-US user sees App Store prices in
   their own currency and their whole budget in dollars. Ship USD-only, or wire up the column that
   is already there? Affects 39 files.
2. **Accent palette vs. the tab bar.** Fixing finding 1 makes the focused tab label *and* icon
   near-black on ten of twelve accents. Correct and legible — but the pill will read lighter than the
   current mock. Confirm that is the intended look before Pia or Paulo respec anything around it.
3. **Section heading size.** I propose 17px semibold. This changes the visual weight of the Cards and
   Insights tabs (currently 20px/19px). Your call on whether Cards should stay heavier.
4. **`welcome.tsx` copy.** The "Track / …" construction needs rewriting, not patching. Do you want
   Mia to take the onboarding copy pass, or should Pia propose replacements inline?
5. **Destructive colour.** Adding a `danger` token means red moves slightly in light mode too
   (`#DC2626` → a warmer brick consistent with `moneyOut`). Acceptable, or must the current red be
   preserved exactly in light mode?
