## 2. Item 1 — Daily receipts reminder

> "Add a daily receipts reminder as a push notification. The user sets the time when to show the
> reminder, but the default will be 8pm."

### 2.1 Mechanism: server-sent, not locally scheduled. Decided, with the evidence.

I traced the existing reminders end to end before choosing:

- `supabase/migrations/20260829100012_push_schedule.sql` schedules `skip-send-push` on pg_cron at
  `*/15 * * * *`, posting to `…/functions/v1/send-push` with an `X-Cron-Secret` the database minted
  for itself.
- `supabase/functions/send-push/index.ts` calls `reminders_due()`, then posts to APNs directly with
  an ES256 provider token, retries against the other APNs host on `BadDeviceToken`, and stamps
  `reminders.last_sent_on` **only on a successful delivery**.
- `supabase/migrations/20260829100010_reminders_due.sql` decides "due" entirely in the user's own
  zone: `(now() at time zone coalesce(p.timezone,'UTC'))`, comparing a bare local `remind_at`
  against local time, and refusing anything already sent on that local date.
- `src/api/push.ts` stores the device token and `profiles.timezone` on every launch (commit
  4afb0f0), and asks for permission only behind a deliberate tap.
- **`grep` for `scheduleNotificationAsync` / `SchedulableTriggerInputTypes` across `src`, `modules`
  and `supabase` returns nothing.** There is no local scheduling in this app at all.

So the house mechanism is server-sent, and the receipts reminder follows it. I considered
`SchedulableTriggerInputTypes.DAILY` (`DailyTriggerInput { hour, minute, type }`, confirmed present
in the SDK 57 notifications reference) and rejected it as the mechanism:

- It would be the only reminder in the app that lives on the phone, so we would own two delivery
  paths, two dedupe stories and two places to change copy.
- It cannot answer "was a receipt already logged today?" without a network read at fire time, which
  a local trigger does not get.
- It would fire per device rather than per account.

The one real cost of the server path: cron granularity. A reminder set to 20:00 is delivered by the
run at 20:00–20:14. That is already true of every bill reminder, and the time picker's `MINUTE_STEP`
means people cannot choose finer than that anyway. Stated so nobody reports it as a bug.

### 2.2 Diego — schema and hooks (do this first; the other two need the contract)

The existing `reminders` table cannot hold this. Its check constraint is
`num_nonnulls(bill_id, subscription_id, card_id, bank_account_id) = 1`, and the upsert in
`src/api/reminders.ts` resolves against a four-column conflict target. A receipts reminder points at
nothing. Do **not** relax that constraint — it is what makes "one reminder per thing" true.

**Recommended shape: three columns on `profiles`.** The profile row already exists for every
account, `reminders_due()` already joins `profiles` for the timezone, and RLS on `profiles` is
already correct. A new table would need its own policies for one row per user.

```sql
alter table public.profiles
  add column if not exists receipt_reminder_enabled      boolean not null default false,
  add column if not exists receipt_reminder_at           time    not null default '20:00',
  add column if not exists receipt_reminder_last_sent_on date;
```

`time` with no zone, for the same reason `reminders.remind_at` is: eight in the evening means eight
in the evening wherever they are. Default `20:00` is the Founder's default, stored rather than
applied in JS, so the server and the app cannot disagree about it. Default `enabled = false`:
nobody who has not asked gets messaged.

**The RPC. This signature is the contract with Dilip — agree it before either of you starts.**

```sql
create or replace function public.receipt_reminders_due()
returns table (
  user_id    uuid,
  local_date date,
  title      text,
  body       text
)
language sql
security definer
set search_path = public
```

Mirror `reminders_due()` exactly, including its "late is a reminder, never is a bug" semantics:

- due when `receipt_reminder_enabled`
- **and** `receipt_reminder_at <= (now() at time zone coalesce(p.timezone,'UTC'))::time`
- **and** (`receipt_reminder_last_sent_on is null` or `<> ` today's local date)
- `revoke all … from public, anon, authenticated;` — the scheduler is the only caller.

Copy, from the Founder, verbatim:
- title: `Receipts`
- body: `Any receipts from today? Log them before you forget.`

The "already logged today" skip is a Founder decision (§6, question 4). Write the function so the
skip is one `and not exists (…)` clause, and leave it commented out behind the decision rather than
guessing.

**Hooks.** Put them in `src/api/reminders.ts`, not `queries.ts`:

- `useReceiptReminder()` — its own `select` of the three columns via the `useOwnerQuery`/
  `withTimeout` pattern, returning `{ enabled, remindAt }` with `remindAt` trimmed to `HH:MM`
  (`row.remind_at.slice(0,5)`, as `useReminderChoice` already does).
- `useSetReceiptReminder()` — `{ enabled, remindAt? }`, an `update` on `profiles`, invalidating its
  own key. When `enabled` is true it must call `enableReminders(userId)` first, exactly as
  `useSetReminder` does at `src/api/reminders.ts:167-169` — a reminder saved on a phone that was
  never asked for permission is a promise we cannot keep.
- Export `DEFAULT_RECEIPT_REMIND_AT = '20:00'` beside `DEFAULT_REMIND_AT`, so Dana does not hardcode
  it.

Keeping this out of `useProfile` is deliberate: the profile query backs the dashboard header and the
tile order, and invalidating it every time somebody drags the clock is a dashboard re-render for no
reason.

**Acceptance**
1. Migration applies on a fresh database and is idempotent (`if not exists` throughout), and applies
   on top of the current schema without touching `reminders`.
2. `receipt_reminders_due()` returns nothing for a disabled account, nothing for an enabled account

3. Prove the zone actually bites: one account on `Pacific/Auckland` and one on `America/New_York`,

The SQL is proven by the transcript, not by jest. Do not deploy anything.

## 3. Item 2 — Ascending order everywhere (Dana)

> "Make all the transactions ascending order, that means today will be at bottom and yesterday on
> top, throughout the app everywhere."

### 3.1 The rule, stated precisely

**Oldest day at the top, newest day at the bottom. Today is the last dated group. Rows with no date
still trail the list.** Within a single day, order is unchanged.

That last clause matters and is why this is smaller than it looks. Every sort in the app already
tie-breaks same-day rows *ascending by id* and only the day runs descending — see
`src/api/queries.ts:940`, `src/lib/card-ledger.ts:419` and `src/app/(tabs)/transactions.tsx:137`,
all of the form `a.date === b.date ? a.id.localeCompare(b.id) : b.date.localeCompare(a.date)`.
So flipping the **day** order alone gives exactly what the Founder asked for, and nothing inside a
day moves. Receipts carry a date and no time, so there is no finer chronology to honour.

**Where it lives:** at the call sites, as an explicit `direction: 'asc'`. Do **not** flip the
default in `src/lib/group.ts:29`. A silent default change is invisible in review and would reach
call sites added later by somebody who never read this plan. `groupByDate` keeps both directions and
keeps its tests for both.

### 3.2 Already compliant — change nothing

Future-dated lists are already ascending, which is the literal rule: nearest day at the top,
furthest at the bottom.

- `src/app/(tabs)/home.tsx:255` — "Coming up", `direction="asc"`.
- `src/app/bill-plans.tsx:97` — upcoming bills, `direction: 'asc'`.

## 6. Decisions for the Founder

1. **"Coming up" ordering.** Home's upcoming week, upcoming bills and upcoming renewals already run
   ascending (nearest day at the top, furthest at the bottom). That is both "nearest first" and
   "ascending", so I am leaving them as they are. Confirm — the alternative reading is that the
   *next* thing due should sit at the bottom nearest the thumb, which would make the two halves of
   the Home screen run in opposite directions.
2. **How far does "everywhere" reach?** Three lists are dated but are not transactions:
   the **Savings months** list, the **Notifications** list (charges that already went out), and the
   **Splits groups** list (ordered by when the group was created). My default is: flip Savings and
   Notifications, leave Splits groups alone. Savings is the risky one — `insights.tsx` reads "the
   three most recent months" by taking the first three of that list.
3. **Scroll position.** Ascending means the newest rows are at the *bottom*, below the fold. Opening
   Transactions will land on the oldest week in the period unless we scroll the list to the end on
   open. That changes how every list screen feels and is a design call (Priya/Pia), not something I
   want a developer choosing mid-task. Without a decision, lists open at the top showing the oldest
   rows.
4. **Should the daily receipts reminder skip days when a receipt was already logged?** Cheap to
   build — one `not exists` clause in the SQL. My recommendation: **yes, skip.** "Any receipts from
   today?" arriving at 8pm on a day somebody already logged three receipts teaches them to ignore
   the notification. The counter-argument: receipts are often logged for a *past* date, so "logged
   today" and "a receipt dated today" are different questions and we would have to pick one. I would
   use *created today* rather than *dated today*.
5. **Does the receipts reminder need reminders to be on generally?** The app tracks a per-account
   `reminders_enabled_at`. My recommendation: the receipts switch turns it on by itself, exactly as
   saving a bill reminder already does, so a user who wants only this one gets only this one.
6. **Pro gating.** Receipt *scanning* is Pro (`WALL.receiptScan`), adding a receipt by hand is free.
   My recommendation: the reminder is **free**. Nudging a free user toward a feature they cannot
   fully use is how a reminder becomes an advert.
7. **Timing precision.** The scheduler runs every 15 minutes, so a reminder set to 8:00 pm arrives
   between 8:00 and 8:14. Already true of every bill reminder. Acceptable, or do we tighten the
   cron?
8. **Receipt images.** The `receipt-images` storage bucket, the `receipts.image_path` column and the
   account-deletion cleanup all exist and are never written to, because the app promises in Privacy
   and on the paywall that receipt photos never leave the phone. Either the dead infrastructure goes
   or the promise changes. Founder's call, and it should not sit in this state.
9. **Loan day-count change.** If Drew's correction changes the figures for loans people have already
   saved, do those loans get recalculated, or grandfathered? Answer this before he finishes, not
   after.
